**代码基线**：`24f21cd`（feat: 归档以主播为顶层）
**审查范围**：`app/` 全部 24 个 Python 文件（约 5,100 行）+ 前端 3 个文件（2,087 行）+ 部署/CI/依赖/脚本

## 一、总体结论

代码整体**架构方向正确**（routers → services 单向分层，无反向依赖；归档布局、路径安全、敏感项脱敏、重启恢复等近期重构质量较高），但存在**三类系统性风险**：

| 类别 | 核心问题 | 后果 |
|---|---|---|
| **并发与状态一致性** | 录制态存在 4 份真相（`rooms.is_recording` / `monitor._room_states` / `recorder.active_processes` / `recordings.status`），无 per-room 锁、无状态机 | 双 ffmpeg 同路径写、并发 finalize 交错、孤儿进程、场次永不收敛 |
| **错误语义丢失** | 适配器把「网络失败/风控/空数据/真下播」压成同一个 `is_live=False`；ffmpeg 退出原因不落库 | 网络抖动被当成下播 → 在录场次被切碎；失败无痕不可追溯 |
| **工程基建缺失** | 0 测试、0 lint、0 CI 质量门、无迁移框架、lock 与镜像 Python 版本不匹配 | 上述问题无法被回归捕获，重构只能靠自觉 |

**评级**：功能可用但**不适合无人值守长期运行**。建议按第七节顺序修复，P0 项（尤其数据丢失类）应优先处理。

## 二、P0 严重问题（数据丢失 / 录制卡死 / 功能失效）

### 2.1 数据丢失类

**P0-1 `finalize` 合并失败仍标记 completed，碎片永久失去 DB 引用**
`app/services/monitor.py:528-559`
`merge_recordings` 失败时只记一行 error 日志，随后**无条件**执行 `status="completed"`、`part_paths=None`、`file_size=0`、`file_path` 指向尚未生成的 `final_path`。原始 part 文件仍在磁盘但已无任何 DB 记录指向它们，且 `_expand_parts` 仅在 finalize 内部使用 —— 这些碎片再也无法被合并、被同步、被 UI 列出。
→ **影响**：一次 ffmpeg concat 失败即造成不可恢复的"录制记录存在但文件不存在"（前端可下载但 404）。
→ **修法**：finalize 收尾前校验 `os.path.isfile(final_path) and size > 0`；失败则置 `status="failed"` + `error_message` 并**保留 `part_paths`**，提供重试合并入口。

**P0-2 先 spawn ffmpeg 后写 DB 行，commit 失败即产生无主进程**
`app/services/monitor.py:372-400`（spawn 在 `recorder.py:187`，建行在 396）
`recorder.start_recording` 成功后才创建 `Recording` 行并 commit；若 commit 抛异常，被 `:342` 的 `except Exception` 捕获仅记日志。此时 ffmpeg 存活，但 `rooms.is_recording` 仍为 False、无 Recording 行 → 下一轮 `:313` 走"开播未录制"分支再调 `_start_recording`，被 recorder 以"已在录制中"静默拒绝；`:330` 的断流检查因 `room_is_recording=False` 被跳过 → **该场次永不 finalize**，进程一直录到磁盘满，文件无 DB 归属（重启时 `_recover_stale_recordings` 也查不到它）。
→ **修法**：先写 `status="recording"` 行（或 pending 占位）再 spawn；spawn 之后任何 DB 失败必须 `stop_recording` 补偿。

### 2.2 录制卡死类

**P0-3 ffmpeg 的 stdout/stderr PIPE 全程不读取 → 管道写满后录制静默停住**
`app/services/recorder.py:187-190`（创建）+ `:259-279`（仅在进程退出后才 read）
已实测复现：向 stderr 大量写入且不被消费时，进程**无法退出**（超时阻塞）。`-loglevel warning` 在断流重连、签名 URL 过期时会连续刷警告，长录制必然填满 64KB 管道缓冲。
→ **影响**：ffmpeg 阻塞在写 stderr，但进程仍存活 → `is_recording()` 返回 True、前端显示"录制中"，实际零字节增长，直到磁盘/用户察觉。且 `stop_recording` 路径从不读 stderr，**退出原因全部丢失**。
→ **修法**：`-loglevel error` + stderr 重定向到文件，或创建后立即起 drain task 持续消费并保留尾部 N KB；finalize 时把退出原因写入 `Recording.error_message`。

**P0-4 `_finalize_session` 在事件循环里同步跑最多 30 分钟的 ffmpeg**
`app/services/monitor.py:528`
`file_manager.merge_recordings` 内部是 `subprocess.run(..., timeout=1800)`（`file_manager.py:310`），此处**直接同步调用**；而同样功能的 `_daily_merge_inner` 在 `:638` 正确使用了 `await asyncio.to_thread`。合并期间整个事件循环被阻塞：所有 API 请求、监控循环、作品下载全部停摆。
→ **修法**：改为 `await asyncio.to_thread(...)`，与 `_daily_merge_inner` 保持一致。

**P0-5 `start_recording` 锁只包住"已在录制"检查，spawn 与登记在锁外 → 双 ffmpeg 同路径写**
`app/services/recorder.py:174-195`
`async with self._lock` 仅覆盖 `:175-177` 的存在性检查，`create_subprocess_exec`（`:187`）与写 `active_processes`（`:194`）都在锁外。已实测复现：两个并发调用**都能通过检查**。
→ **影响**：监控循环 + API 手动开始 + `check_room_now` 三路并发时，两个 ffmpeg 以 `-y` 写同一 output_path → 文件损坏；后写入的 dict 覆盖前者 → 前者失联成孤儿。
→ **修法**：锁覆盖"检查 + spawn + 登记"整段，或先占位（`active_processes[id] = PENDING`）再 spawn，失败回滚。

**P0-6 `stop_recording` 先 pop 再 SIGTERM，kill 失败即留下不可管理孤儿**
`app/services/recorder.py:210-211`（pop）→ `:226-243`（SIGTERM/超时/SIGKILL，异常仅记日志返回 False）
进程被 pop 后若 SIGTERM 未被处理、`wait_for` 超时后 killpg 抛非 `ProcessLookupError` 异常，则进程仍在跑但已不在 dict 中 → `is_recording()` 返回 False → 监控判"断流"→ 启动新 ffmpeg，旧进程永久孤儿。
→ **修法**：只在 `wait()` 确认 reaped 后 pop；失败时保留登记并标 orphan，finally 兜底 kill + wait。

**P0-7 无 per-room 锁，`_finalize_session` 可被 4 个入口并发进入**
`app/services/monitor.py:326, 339, 486-563`；入口：监控循环、`check_room_now`（`rooms.py:384/421`）、手动停止（`rooms.py:472`）、`_handle_finished_recordings`（`:747`）
两次 finalize 并发 → 都 select 同一 recording 行、都对**同一 final_path** 跑 concat（`-y`）、都在 `:535-539` 删源 part → 输出被两路 ffmpeg 交错写坏，part 在读取中被删除。
→ **修法**：per-room `asyncio.Lock`（`dict[room_id]`）串行化 start/reconnect/finalize；finalize 用 CAS：`UPDATE recordings SET status='completed' WHERE id=? AND status='recording'`，`rowcount=0` 直接返回。

### 2.3 功能失效类

**P0-8 适配器吞掉所有异常并返回 `is_live=False` → 网络抖动被当成下播**
`app/services/platform/douyin.py:71-74`、`bilibili.py:91-94`、`kuaishou.py:190-193`（`except Exception: logger.error(...)` 后 `return info`），`RoomInfo.is_live` 默认 False（`base.py:28`），无"探测失败"标志。
`app/services/monitor.py:324-327` 见 `not info.is_live and room_is_recording` 就立即 `_finalize_session()`。
→ **影响**：一次网络抖动 / 风控 / 平台 JSON 结构变化，正在录制的场次被提前 finalize + 合并，下一轮又重开新场次 → **同一直播被切成多段**，断流续写逻辑失效。
→ **修法**：`get_room_info` 返回 `Optional[RoomInfo]`（None = 探测失败）；monitor 探测失败时**不做任何状态迁移**，并要求连续 N 次（如 3）失败才判定下播。

**P0-9 抖音 `X-Bogus` 是假签名，且必被塞进请求头**
`app/services/platform/douyin.py:184-202`
`md5(query) + timestamp` → base64 → 截 28 字符，是伪造值而非真实算法；`_get_ms_token` 为随机串（`:177-182`）。抖音服务端对非法 `X-Bogus` 的处置比不传更严（返回 `status_code != 0` / 空 data）。
→ **影响**：叠加 P0-8，抖音直播间可能**长期检测不到开播**。
→ **修法**：删除该假签名分支（不传，或用 vendor 的 ABogus 按 live 路径真实签名）；msToken 从真实接口获取。

**P0-10 作品检查用全局单锁包住整条回填翻页链 → 全站排队**
`app/services/works_monitor.py:287-288`（`async with self._check_lock` 覆盖整个 `_check_room_works_inner`），其中 `_backfill()` 逐页 `asyncio.sleep(2~5)`、最多 500 页，而 `works_backfill_limit` 默认 **0 = 不限量**。
→ **影响**：一个历史作品多的主播回填期间，其余所有主播的增量检查、以及 `POST /api/works/check/{id}` 全部排队数十分钟到数小时；用户点"立即检查"看起来无响应。
→ **修法**：锁粒度改 per-room；或只在 DB 写入段加锁，网络翻页在锁外；`_backfill` 加总时长上限。

**P0-11 未注册平台直接导致 500（已用 TestClient 复现）**
`app/routers/rooms.py:178` 与 `:281`：`PlatformFactory.get_platform_class(platform).extract_room_id(url)` —— `get_platform_class` 返回 `None` 时属性访问抛 `AttributeError`。
复现：`POST /api/rooms {"url":"https://live.douyin.com/123","platform":"youtube"}` → **500 Internal Server Error**。
→ **修法**：`platform` 必须走白名单校验（`get_all_platforms()`），非法值返回 400；或对该表达式做 None 保护。

**P0-12 清空 `output_dir` 会持久破坏运行时配置（已复现）**
`app/routers/system.py:272-281`：先 `setattr(settings, "output_dir", "")`，**之后**才 `os.makedirs(settings.output_dir)`。已复现 `os.makedirs('')` 抛 `FileNotFoundError` → 500，但**内存里的 settings 已被改成空串**，后续录制/文件管理按相对路径工作直到重启。
→ **修法**：先校验（空值 400）再 apply；或 apply 前深拷贝快照、失败逐字段还原。

**P0-13 开启 `LIVE_RECORDER_API_TOKEN` 后自带网页完全不可用**
`app/static/js/app.js:4-7`：`API` helper 的 `fetch` 不发送任何 `Authorization` 头；`<video>` 播放（`:563`）与下载链接同理。
→ **影响**：README:269 已如实说明这一点，但这意味着"可选鉴权"与"可用 UI"互斥 —— 一个安全开关直接让产品不可用，属设计缺陷而非文档问题。
→ **修法**：前端登录后把 token 存 `sessionStorage` 并注入所有 fetch（含播放用 blob URL）；或改为 Cookie/Session 鉴权使 `<video>`/下载天然可用。

**P0-14 容器停止预算与关闭路径不匹配 → mp4 在写 moov 前被 SIGKILL**
`docker-compose.yml`（全文无 `stop_grace_period`）+ `app/services/monitor.py:99-113`
Docker 默认 SIGTERM 后 **10s 即 SIGKILL**；而 `stop()` 先等后台合并任务最多 8s（`:99-106`），再对**每个** active 进程逐个 `wait_for(process.wait(), timeout=10)`（`:109-113`）。3 路并发录制 = 8 + 30s，必然被打断。
→ **影响**：这正是 `OPTIMIZATION_REPORT` 中「P0-3 已修（让 mp4 正常写 moov）」的**回退点**。
→ **修法**：compose 加 `stop_grace_period: 60s`（且 > ffmpeg 等待预算），或 recorder 并发 `gather` 停止 + 单项 timeout 降到 5s。

## 四、P2 质量与优化建议

### 4.1 后端

- **异常吞噬**：`except Exception` 共 31 处、`pass` 18 处（`monitor.py` 9、`works_monitor.py` 9）。多处仅 `logger.error` 后继续，导致故障无闭环。
- **`get_db` 对所有请求（含 GET）都 commit**（`database.py:94-104`）：GET 也开事务并提交，语义冗余且放大锁竞争。
- **`limit` 参数无下限校验**（`recordings.py:30`、`system.py:136`）：`?limit=-1` 在 SQLite 中等价 `LIMIT -1` = **返回全表**（已实测）。
- **`get_file_list` 直接改写缓存列表条目补 platform**（`file_manager.py:84-86`），缓存读写无锁（多线程 `to_thread` 并发）→ TTL 内返回陈旧平台。
- **`_notify` 每次新建 `httpx.AsyncClient` 且在 `_check_room`/`_finalize` 内 await**（`monitor.py:755-756`）→ 每房间最多 +10s 串行延迟。
- **`create_task` 无 done callback 取异常**（`monitor.py:52-54, 570-572`）→ `Task exception was never retrieved` 警告，合并/通知异常静默。
- **duration 用墙钟**（`monitor.py:546, 656`），daily merge 再把各段相加 → 断流空档计入时长，合并后虚高。
- **启动恢复把 recording→failed 但不尝试合并已有 part**（`monitor.py:179-189`）→ 崩溃后碎片永远无法变成可播放文件。
- **`/api/system/sync/run` 直接 await 全量同步**（`system.py:307` + `sync_service.py:101-123`）→ 单个几十 GB 文件把 HTTP 请求挂住数小时，无进度/超时。
- **`_fetch`/`_post` 是死代码**（`base.py:136-164`，全项目零调用），UA 还与 `WORKS_UA` 不一致。
- **pyflakes 实测**：8 处未使用导入（`config.py:6` `Field`、`recordings.py:3` `HTTPException`、`recorder.py:5,9`、`sync_service.py:17`、`file_manager.py:9`、`douyin.py:187` `struct`、`bilibili.py:6,8`、`base.py:6` `re`）+ `monitor.py:631` 未使用变量 `final_path`。
- **`abogus.py:388` 引用 `value_e` 存在跨迭代依赖**：pyflakes 报 undefined name；实测因循环首轮必走 `if` 分支而侥幸不触发 NameError，属脆弱写法，建议显式初始化。
- **`_clean_empty_dirs` / `delete_file` 用 `startswith(base)` 缺 `os.sep`**（见 P1-22）。

### 4.3 部署与工程

- **`.dockerignore:1`** 模式 `__pycache__` 在 Docker 里按完整相对路径匹配，**只命中根级**，不命中 `app/__pycache__`；实测仓库内 `app/**/*.pyc` 有 27 个会被 `COPY app/` 带进 3.11 镜像（3.11 magic 不匹配会重编译，无功能危害但属噪声）。应改 `**/__pycache__`、`**/*.pyc`。
- **`main.py:47-65` 挂载自检漏查 data 目录**：只查 `output_dir` 与 `sync_root`，**不查 `get_data_dir(database_url)`** —— `./data` 漏挂则 SQLite 落容器可写层，重启丢全部主播/记录（比丢录像更严重）。且用 `os.path.ismount` 判挂载点，把 output_dir 设为挂载点子目录会**假告警**。
- **`docker-compose.yml` 无 `logging:` 段**：应用只写 stdout（`main.py:19-23`），Docker json-file driver 默认无 max-size → 7×24 部署下宿主机日志文件可涨到 GB 级。
- **`./logs` 卷空转**：compose 挂载 `./logs:/app/logs`、Dockerfile `mkdir /app/logs`，但代码**只用 stdout logging.basicConfig**，无任何 `FileHandler` → 该卷永不写入，用户以为有文件日志。
- **`config/` 双重来源**：既烘进镜像（`Dockerfile:40`）又被 compose `:ro` 挂载；裸 `docker run`（README:68 示例未挂 config）用的是镜像内烘焙的 config.ini → 两套配置静默分叉。
- **无 `USER` 指令**：容器以 root 运行；无 `init: true`（PID 1 信号转发）、无 `read_only`/`security_opt`/`pids_limit`。
- **`data/runtime_config.ini` 残留 3 个废弃键**（`video_quality`/`max_retries`/`retry_delay`），`_apply_ini` 静默跳过 → 证明配置层无 schema 校验，拼错/过期键永远静默失效。
- **依赖无 hash**：`pip install` 未用 `--require-hashes`，lock 无 `--hash` 行 → 镜像源（compose 默认阿里云）被投毒时无防线。

## 五、架构层面观察

1. **"四份真相、零个 owner"**：房间录制态同时存在于 `rooms.is_recording`(DB)、`monitor._room_states`、`recorder.active_processes`、`recordings.status`，无单一权威、无 per-room 锁 → **P0-1/2/5/6/7 全部是这一点的派生**。
   → 建议引入 `SessionManager`：per-room `asyncio.Lock` + 显式状态机（`idle→starting→recording→finalizing→idle`）+ DB CAS 迁移；monitor/API 只发命令，不直接改状态。

2. **错误语义缺失是跨模块共同根因**：适配器把"网络失败/风控/空数据/真下播"压成同一个 `RoomInfo(is_live=False)`；works 把"可重试/永久失败"压成同一个 `RuntimeError`。
   → 建议 `base.py` 定义 `PlatformError(kind: retryable|auth|risk|not_found|parse)`，`get_room_info` 返回 `Optional[RoomInfo]`；`Work` 加 `attempts` + `next_retry_at` 支持退避。

3. **monitor/works_monitor 骨架重复**：`monitor.py:162-194` ↔ `works_monitor.py:76-94`（启动恢复）、`monitor.py:43-55` ↔ `works_monitor.py:62-63`（磁盘告警）、两套 `_loop` + 分段 sleep。
   → 抽 `BaseMonitor`（loop + 恢复 + 磁盘闸门），差异下沉子类。

4. **全局单例在 import 期构造**：`monitor`/`works_monitor`/`sync_service`/`recorder`/`file_manager`/`platform_manager` 全部模块导入时实例化；`database.py:9-15` 在 import 时 `os.makedirs` + `create_async_engine`；`grep app.state` **零命中**。
   → 后果：`import app.main` 连带建库、建目录、建 httpx client；无法同进程起两个隔离实例；服务生命周期与 FastAPI 耦合但不可替换。
   → 建议改 `app.state.monitor` 等，lifespan 内构造注入。

5. **`settings` 单例没有"重绑定漂移"问题**（`grep "settings ="` 仅 `config.py:231` 一处赋值，12 处同对象读取 —— 这点是安全的）。真正风险是**原地可变** + 无 `validate_assignment` + 无并发保护（见 P1-26）。

6. **循环导入当前不存在但结构脆弱**：`archive→recorder`、`file_manager→archive`、`works_monitor→archive/file_manager/recorder`、`monitor→archive/recorder/file_manager` 目前是单向 DAG，但 `archive`↔`file_manager` 靠"archive 不 import file_manager"的默契维持；任一方为复用加一行 import 即成环。

7. **阻塞调用无统一规约**：`file_manager.merge`(310)、`get_disk_usage` 已走 `to_thread`，但 `monitor.py:528` 直接同步调同一函数；`os.walk`/`os.stat` 在 `monitor._expand_parts`(703-707) 跑在事件循环。
   → 建议硬性规则"所有 ffmpeg/文件遍历一律 `to_thread`"，并在 CI 加 grep 检查。

8. **存储层无完整性校验**：finalize 只 `getsize`，从不 `ffprobe` 验证产物；无 fsync。
   → 建议 finalize 加 ffprobe 校验，失败落 failed。

9. **三个适配器 60% 代码是同一模板**：`match_url`（子串 in）、`extract_room_id`（正则表）、`get_room_info`（try 包全部 + 三套 headers）、`_api_headers` 各写一遍。
   → 上移到 base：`DOMAINS`/`ROOM_ID_PATTERNS` 类属性 + `_api_headers()` 模板方法；base 里已有 `_fetch/_post` 却没人用（"共享层建了但没接上"）。

10. **`PlatformManager` 用"close 旧实例"实现配置热更新**，天然与并发在途请求冲突；而真正想复用是 httpx 连接池。
